## 2026-10-21 — A1: building the evaluation corpus

**Environment.**
- Hypothesis: Python 3.14 might lack wheels for `tokenizers`/`tiktoken`.
- Result: everything installed and imported (versions in D-02), so the 3.12 fallback was not needed.

**Choosing a corpus.**
- Leaning: FLORES-200, because it is parallel. I read the primary sources before deciding (D-03):
  - **FLORES-101 paper:** contiguous sentences per article, translated *from English*, QA threshold 90/100.
  - **Petrov et al. §3:** the premium is |t(s_A)|/|t(s_B)| on FLORES-200, the same comparison we need.
  - **IN22 repo:** IN22-Gen 1,024 sentences, IN22-Conv 1,503 sentences.
- Surprise: the FLORES+ card asks that the data not be used for training and not be redistributed publicly. That reopened our plan to commit the text (D-11, proposed).

**Access.**
- HF `facebook/flores` is gated (login plus accepting conditions).
- The original tarball is ungated: HTTP 200, 25,585,843 bytes. Chose the tarball for credential-free reproducibility and recorded the SHA-256.

**TDD, corpus integrity.**
- Wrote 23 tests first; all failed with `FileNotFoundError` (intended).
- Wrote `prep.py` (byte-for-byte copy plus manifest); 23 passed.
- Dead end: `wc -l` gave 997/1,012, but it counts newlines, not lines. The tests count lines properly, so a missing final newline couldn't hide a sentence.

**Alignment heuristics.**
- Thresholds were set *before* looking: <=1% of lines outside the length-ratio band 0.2–5, and >=60% number match.
- Worry: Indic translations might use native digits and fail the number check.
- Result: the worry was wrong. ASCII digits are used, and the match is 99.2–99.7%. The length ratio stays within 0.49–2.03.
- Revision: the thresholds were very loose. I kept them and reported the actual margins rather than tightening after the fact.

**NFC surprise.**
- Assumption: NFC is a no-op on clean data.
- Result: it changes 90 + 93 Hindi lines (~9%), 17 Kannada and 4 Tamil. Hindi FLORES uses precomposed nukta letters (U+0958–095F), which NFC *decomposes*.
- Revision: H-A7 ("NFC is harmless") is now open, not presumed harmless. The prepared text stays raw so A2 can measure NFC's effect on tokens.

**Grapheme clusters.**
- First probe: `regex` `\X` gave 3 clusters for a Hindi word, and I almost concluded that "\X handles conjuncts".
- Wrote characterisation tests across scripts. The ka+virama+ssa conjunct is 1 cluster in Devanagari, Telugu and Malayalam, but **2 in Kannada and Tamil**.
- Revision: the one-word probe generalised wrongly. Grapheme clusters are not a uniform unit across our languages (D-05).

**Corpus stats** (generated by `stats.py`; a test checks that `stats.json` is not stale):
- Same content takes 1.17× English words in Hindi, 0.74× in Kannada and 0.77× in Tamil. Bytes are 2.56–3.19×; code points 1.00–1.17×. That is first evidence for the A2 conceptual issue: word-based fertility mixes tokenizer cost with morphology.
- Small bug in my own stats: topic labels had mixed case ("travel" 323 vs "Travel" 174). Fixed by case-folding; travel = 497.

**Sample-size check.**
- Hypothesis: article clustering (3–5 contiguous sentences per article) would widen CIs a lot.
- Result: the clustered and i.i.d. bootstrap CIs are almost identical for the codepoint ratio (hin 0.991–1.004 vs 0.991–1.003). The concern mattered less than expected for this statistic. I'll re-check it for token ratios in A3.

## 2026-10-21 (later) — committing A1; a line-ending bug

**Decisions.**

**Line endings.**
- Machine has `core.autocrlf=true`. I wrote `.gitattributes` (LF for authored text; `-text -eol` for `starter_kit/**` and the FLORES text) and checked every file with `git check-attr`.
- `cmp` confirms `starter_kit/` is byte-identical to the provided kit.

**Dead end / bug.**
- My earlier check reported "no CRLF files". When committing A1, git warned that `stats.json` and `manifest.json` had CRLF.
- Measured: 282 and 45 CR bytes. The cause is that `Path.write_text` translates `\n` to `\r\n` on Windows.
- The earlier check (`grep $'\r'`) was broken in this shell: it does not find a CR that `tr -cd '\r' | wc -c` does find.
- The committed blobs were already LF thanks to `.gitattributes`.
- Fix: a test asserting no CR bytes (red: 2 failed) -> `newline="\n"` -> green (44 passed). Committed separately as `edd8a50`.

**Same bug, a second time, in my own tooling.**
- After the docs commit (`4bedafe`), git warned about CRLF in `docs/decision.md` on disk: 130 CR bytes.
- Cause: an earlier one-off Python edit script that wrote the file in text mode, the same Windows `\n` -> `\r\n` translation.
- The committed blob had 0 CR. I converted the working copy to LF and confirmed with `cmp` that it is identical to the committed version.
- Lesson: on this machine, any Python write must pass `newline="\n"` (or write bytes).

**Re-measured, not assumed:** CR bytes per committed file.
- 0 everywhere except `starter_kit/bench/bench_log.csv`: 14 CR in 14 lines.
- That file is CRLF in the *original* kit (checked against the source folder), so it is original data and `-text` correctly preserves it.
- Relevant later: anything parsing it (Part B) must handle `\r\n`.
