**Alignment heuristics.**
- Thresholds were set *before* looking: <=1% of lines outside the length-ratio band 0.2–5, and >=60% number match.
- Worry: Indic translations might use native digits and fail the number check.
- Result: the worry was wrong. ASCII digits are used, and the match is 99.2–99.7%. The length ratio stays within 0.49–2.03.
- Revision: the thresholds were very loose. I kept them and reported the actual margins rather than tightening after the fact.

**NFC surprise.**
- Assumption: NFC is a no-op on clean data.
- Result: it changes 90 + 93 Hindi lines (~9%), 17 Kannada and 4 Tamil. Hindi FLORES uses precomposed nukta letters (U+0958–095F), which NFC *decomposes*.
- Revision: H-A7 ("NFC is harmless") is now open, not presumed harmless. The prepared text stays raw so A2 can measure NFC's effect on tokens.

**Grapheme clusters.**
- First probe: `regex` `\X` gave 3 clusters for a Hindi word, and I almost concluded that "\X handles conjuncts".
- Wrote characterisation tests across scripts. The ka+virama+ssa conjunct is 1 cluster in Devanagari, Telugu and Malayalam, but **2 in Kannada and Tamil**.
- Revision: the one-word probe generalised wrongly. Grapheme clusters are not a uniform unit across our languages (D-05).

**Corpus stats** (generated by `stats.py`; a test checks that `stats.json` is not stale):
- Same content takes 1.17× English words in Hindi, 0.74× in Kannada and 0.77× in Tamil. Bytes are 2.56–3.19×; code points 1.00–1.17×. That is first evidence for the A2 conceptual issue: word-based fertility mixes tokenizer cost with morphology.
- Small bug in my own stats: topic labels had mixed case ("travel" 323 vs "Travel" 174). Fixed by case-folding; travel = 497.

**Sample-size check.**

- Measured: 282 and 45 CR bytes. The cause is that `Path.write_text` translates `\n` to `\r\n` on Windows.

- The committed blobs were already LF thanks to `.gitattributes`.
- Fix: a test asserting no CR bytes (red: 2 failed) -> `newline="\n"` -> green (44 passed). Committed separately as `edd8a50`.

**Same bug, a second time, in my own tooling.**
- After the docs commit (`4bedafe`), git warned about CRLF in `docs/decision.md` on disk: 130 CR bytes.
- Cause: an earlier one-off Python edit script that wrote the file in text mode, the same Windows `\n` -> `\r\n` translation.
- The committed blob had 0 CR. I converted the working copy to LF and confirmed with `cmp` that it is identical to the committed version.
- Lesson: on this machine, any Python write must pass `newline="\n"` (or write bytes).

**Re-measured, not assumed:** CR bytes per committed file.

  - Direct probe: XLM-R's precompiled normaliser maps raw `ज़` and its NFC form to the same code points and the same token (id 84173).

**Mutation-checker bug (my tool, not the code under test).**
- **What happened:** the F2 mutation run crashed after 11/11 kills. The "F2 branch inverted" mutant made pytest print Devanagari, and the checker decoded the child's output as cp1252, the Windows default. Result: `UnicodeDecodeError` -> stdout `None` -> `TypeError`. The run was *incomplete*, not a pass.
- **Reproducing it test-first took three tries:**
  - Try 1 was red only because `run_tests` had no test-list parameter: the wrong reason.
  - Try 2 passed, because the original run had `PYTHONIOENCODING=utf-8`, so the child wrote UTF-8. Recreated with `monkeypatch.setenv`.
  - It still passed. cp1252 can decode most bytes, failing only on 0x81/0x8D/0x8F/0x90/0x9D, and the UTF-8 bytes of `ज़` contain none of those. The real crash was byte 0x81, as in U+0941 (`E0 A5 81`).
  - Try 3, using U+0941, was **red with the exact original error**.
- **Fix:** the child is forced to `PYTHONIOENCODING=utf-8` and the parent decodes UTF-8 with `errors="replace"`. The regression test is green under both `PYTHONIOENCODING=utf-8` and `cp1252`.
- **Lesson:** a repro that passes for the wrong reason is not a repro. Check the byte-level mechanism.
