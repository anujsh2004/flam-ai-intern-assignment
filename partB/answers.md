# Part B — Capacity reconciliation

Every number below carries an evidence ID `[P#]`. The **Evidence index** at the end maps each ID to a field of `partB/results.json`, which is generated by `python partB/capacity.py` from `starter_kit/bench/{model_spec.md, bench_log.csv}`. `partB/tests/test_answers_evidence.py` checks every entry, and a staleness test keeps `results.json` equal to a fresh rebuild.

Reproduce: `python partB/capacity.py && python -m pytest partB/tests`

## B1 — KV-cache bytes per token and maximum concurrent 4096-token sequences

**(a) Bytes per token, exactly.** K and V are stored for every layer and every KV head (GQA), each `head_dim` long, in fp16:

```
2 (K,V) × 28 layers × 8 KV heads × 128 head_dim × 2 bytes = 114,688 bytes/token      [P1]
× 4096 tokens = 469,762,048 bytes per full sequence (≈ 0.47 GB)                       [P2]
```

The Q heads (24) do not enter the formula, because only K and V are cached. GQA shares each of the 8 KV heads across 3 Q heads.

**(b) Maximum concurrent 4096-token sequences.**

```
KV budget = total × gpu_memory_utilization − weights − non-KV overhead
          = 24e9 × 0.92 − (4.2e9 params × 2 B) − 1.6e9
          = 22.08e9 − 8.4e9 − 1.6e9 = 12.08e9 bytes                                   [P3]
          = 105,329 tokens                                                             [P4]
→ 12.08e9 / 469,762,048 ≈ 25.72 sequences                                              [P5]
```

**The "24 GB" is ambiguous**, so both conventions were computed: with 24 GiB and a 1.6 GiB overhead, the budget holds 118,497 tokens [P6], or **28.93** sequences [P7].

**Check against the log, two independent ways.** The log decides which convention is right.
1. **Cache utilisation at rows with no preemption.** All `batch × (prompt + gen)` tokens are resident at peak, so capacity = resident tokens / `kv_cache_util`. Utilisation is printed to 2 decimals, so each row gives an interval. All 7 usable rows intersect at **[105,138, 105,703] tokens** [P8, P9]. That interval **contains the decimal answer (105,329) and excludes the binary one (118,497).**
2. **Preempting rows.** At batch 32 (7 preempted) and batch 48 (23 preempted), exactly **25** sequences stay resident [P10], which is ⌊25.72⌋. Binary would allow 28.

**Conclusion:** about **25 concurrent 4096-token sequences** fit, and the log supports the decimal-GB reading [P11].

## B2 — The long-context throughput anomaly

**Naive expectation:** throughput rises with batch size. **What the long-prompt sweep (prompt 3584, gen 512) shows instead**, measured in useful tokens per second:

| batch | goodput (tok/s) | wall_clock_s | kv_cache_util | preempted_seqs | TTFT p50 |
|---|---|---|---|---|---|
| 24 | **200.9** [P12] | 61.16 [P15] | 0.93 [P18] | 0 | 500.5 ms [P20] |
| 32 | 173.0 [P13] | 94.71 [P16] | 0.97 | 7 [P22] | 636.9 ms |
| 48 | 162.3 [P14] | 151.41 [P17] | 0.97 [P19] | 23 [P23] | 955.4 ms [P21] |

**The anomaly:** goodput peaks at batch 24 [P24], then *falls* as the batch grows. From 24 to 48 the batch doubles, but the run takes 2.5× longer (61.16 s → 151.41 s).

**Mechanism:**
1. The KV cache holds about 25 sequences of 4,096 tokens (B1).
2. At batch 32 and 48, `kv_cache_util` saturates at 0.97, and the scheduler **preempts** sequences (7 and 23).
3. A preempted sequence loses its KV blocks and must later recompute its 3,584-token prefill: work done twice that produces no extra output.
4. Waiting sequences also start later, so TTFT p50 nearly doubles (500.5 → 955.4 ms).

The rows show it: preemption begins exactly where goodput turns down.

**Proposed change (user decision): cap concurrent sequences at 24** (vLLM `max_num_seqs=24`).
- **Why 24:** it is the largest batch the log shows running with zero preemption.
- **Predicted effect:** the 48-request burst runs as 2 waves of the **logged** batch-24 run, so wall ≈ 122.32 s [P25] and goodput ≈ **200.9 tok/s, +23.8%** over the observed 162.3 [P26, P27].
- **Strength of the prediction:** it uses only logged behaviour, with no extrapolation, and changes nothing about the model's output.
- **Cost:** tail latency. The last requests wait for the first wave (about 122 s vs the observed p95 of 105.4 s [P28]).

**Alternatives evaluated with the same method:**
- **(b) fp8 KV cache:** 57,344 B/token [P29] means about 51.4 sequences fit [P30], so batch 48 would not preempt. A least-squares line through the non-preempting rows (b4–b24), extended to b48, gives wall ≈ 100.5 s [P31] and goodput ≈ **244.5 tok/s, +50.6%** [P32, P33].
  - **Caveats:** that is an extrapolation to twice the largest observed batch, and fp8 KV's effect on output quality is **not measured**.
  - **Status:** **the follow-up experiment.** Measure quality and goodput on L4 before adopting it.
- **(c) Lower `max_model_len`:** no help. Paged KV capacity is in tokens, so the limit changes neither bytes/token nor capacity. Every long request here is exactly 3,584 + 512 = 4,096 tokens, so a lower limit would reject all 48 [P34].

## B3 — The misread column, honest goodput, and what the report should have said

**The misread column is `reported_tok_s`.** It equals **(prompt_len + gen_len) × num_requests / wall_clock_s** on **all 13 rows** [P35], within the log's rounding; generated-only matches **0 rows** [P36]. It counts the *prompt* tokens the user sent as if they were output.

That one misreading produces both of REPORT_v0's conclusions:
- **"Longer prompts give better throughput (1311 vs 883 tok/s at batch 16)."** The long rows count 3,584 + 512 tokens per request; the short rows count 512 + 256. In useful (generated) tokens per second, long prompts are *worse* at every shared batch size. At batch 16: **163.9 vs 294.5 tok/s** [P37, P38].
- **"Batch 48 ≈ 3200 tok/s (scale linearly from ~1600)."** Linear extrapolation of the inflated column, ignoring the KV limit. The log shows batch 48 at 1298.5 reported [P39], which is only **162.3 useful tok/s** [P14], *below* batch 24.

**Honest goodput of the batch-24 long-prompt row, two independent ways:**
1. Generated tokens / wall clock: 24 × 512 / 61.16 = **200.92 tok/s** [P40].
2. The separately logged `reported_tok_s` scaled to its generated share: 1607.4 × 512 / 4096 = **200.93 tok/s** [P41].

They agree within the log's rounding.

**Bounds from the latency columns:** from e2e p95, 177.5 tok/s [P42]; from TTFT p50 + 511 × ITL p50, 247.8 tok/s [P43]. These bracket the goodput but cannot measure it. `e2e_ms_p95` exceeds the run's own wall clock on 12 of 13 rows [P44] (e.g. a single request "taking" 12.86 s in a 10.94 s run). So the latency columns and `wall_clock_s` do not share a start point. This is a data-quality caveat about the log itself.

**What the report should have said:**

> At prompt 3584 / gen 512, the L4 delivers about 200 useful tok/s at batch 24, its best point. Beyond about 25 concurrent 4K-token sequences the KV cache saturates and the scheduler preempts, so batch 48 delivers *less* (about 162 tok/s). Plan capacity at about 200 useful tok/s per L4 for this request shape. Cap concurrency at 24, and evaluate fp8 KV to raise the ceiling. Longer prompts do not improve throughput; they consume it.

## B4 — The one counter that confirms the B2 mechanism

**Pull the scheduler's preemption counter, `vllm:num_preemptions_total`.**
- **If the mechanism is right:** it stays at **0** for batches 4–24 and rises at **≥7** for batch 32 and **≥23** for batch 48. It is "≥" because `preempted_seqs` counts sequences preempted *at least once*.
- **After the cap is applied:** it should read **0** for the same 48-request burst.
- **If the mechanism is wrong:** a non-zero count at batch ≤ 24, or a zero count at 32/48 alongside the goodput drop, would falsify KV exhaustion as the cause. The cause would then be compute or bandwidth saturation, visible as rising ITL without preemption.
